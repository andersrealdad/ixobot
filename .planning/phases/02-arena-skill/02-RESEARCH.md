# Phase 2: Arena Skill - Research

**Researched:** 2026-04-01
**Domain:** Nanobot skill development, sandbox execution, SQLite message bus
**Confidence:** HIGH

## Summary

This phase creates a nanobot skill (`arena-builder`) that receives arena task_queue entries from Phase 1's `arena_trigger.py`, runs each competitor in an isolated sandbox via `agent-gsd.sh`, and produces structured `insights.jsonl` output. The skill is NOT user-invocable -- it is triggered by heartbeat task pickup when the agent name matches `arena-competitor-a` or `arena-competitor-b`.

The integration surface is well-defined and fully inspected. The heartbeat service (`heartbeat/service.py`) fetches pending tasks from `shared-memory.db` WHERE `target_agent = ?`, claims them, formats them into a prompt, and dispatches through `agent.process_direct()`. The skill SKILL.md instructs the agent how to parse the JSON task description and execute the arena workflow. A companion `scripts/arena_run.py` handles the mechanical work: sandbox creation, agent-gsd.sh invocation, insights.jsonl collection, and message_bus posting.

Key constraint: `agent-gsd.sh` uses Claude Code CLI with OAuth/MAX session (no API key). Competitors use `OCTOPUS_MODEL` env var to select Qwen models via Ollama, but the CLI itself still requires Claude OAuth. This is by design -- the competitors run Claude Code CLI in quick mode with model override.

**Primary recommendation:** Build a two-file skill: `SKILL.md` (agent instructions) + `scripts/arena_run.py` (execution engine). The SKILL.md tells the agent to call `arena_run.py` with the task JSON; `arena_run.py` handles all sandbox/subprocess/SQLite mechanics.

## Architecture Patterns

### Recommended Skill Structure
```
nanobot/skills/arena-builder/
  SKILL.md                    # Agent instructions (frontmatter + markdown)
  scripts/
    arena_run.py              # Execution engine (called by agent via exec tool)
```

### Pattern 1: SKILL.md Frontmatter
**What:** YAML frontmatter declares skill metadata for discovery by `skills.py`
**When to use:** Every nanobot skill
**Example:**
```yaml
---
name: arena-builder
description: Execute arena competitor builds in isolated sandboxes. Triggered by heartbeat task pickup for arena-competitor-a/b agents.
user_invocable: false
metadata: {"nanobot":{"requires":{"bins":["claude"]}}}
---
```

Key fields from `skills.py` analysis:
- `name`: directory name match (used for lookup)
- `description`: shown in skills summary XML
- `user_invocable`: if false, not triggered by `/arena-builder` command
- `metadata`: JSON string with nanobot-specific config. `requires.bins` checks `shutil.which()`. `requires.env` checks `os.environ.get()`. `always: true` would auto-load every context (not needed here).

### Pattern 2: Heartbeat Task Dispatch Flow
**What:** How a task_queue entry becomes agent work
**When to use:** Understanding the full execution path

```
arena_trigger.py
  -> INSERT INTO task_queue (target_agent="arena-competitor-a", status="pending")

HeartbeatService._tick()
  -> _fetch_pending_tasks(db, "arena-competitor-a")
  -> _claim_task(db, task_id, "arena-competitor-a")
  -> TASK_QUEUE_PROMPT.format(count=1, tasks=formatted_tasks)
  -> agent.process_direct(prompt, session_key="heartbeat")

Agent loop reads prompt, sees task description JSON
  -> Agent reads SKILL.md (arena-builder loaded in context or read via file)
  -> Agent calls exec tool: python3 arena_run.py '<task_json>'
  -> arena_run.py creates sandbox, runs agent-gsd.sh, collects insights, posts to message_bus
```

**Critical detail:** The heartbeat passes the raw task description (JSON string) as part of `_format_tasks_for_prompt()`. The SKILL.md must instruct the agent to extract the JSON from the task description and pass it to `arena_run.py`.

### Pattern 3: Sandbox Isolation
**What:** Each competitor gets a fresh directory with no cross-access
**When to use:** SKIL-02

```
~/shared-data/DEV/garage/workshop/arena-{bo_id}-{model}/
  instruks.md          # Written by arena_run.py (from task JSON)
  result.json          # Written by agent-gsd.sh
  insights.jsonl       # Written by GSD prompt (must be instructed in the build prompt)
  DONE.md or FLAG.md   # Written by agent-gsd.sh
  .git/                # Initialized by agent-gsd.sh
  .planning/           # Created by GSD if auto/quick mode
```

### Pattern 4: Insights Generation Strategy
**What:** How insights.jsonl actually gets produced
**When to use:** SKIL-04

The `insights.jsonl` is NOT produced by agent-gsd.sh itself -- agent-gsd.sh runs Claude Code CLI which builds the BO. The insights must be requested as part of the build prompt. Two approaches:

**Approach A (Recommended): Post-build extraction by arena_run.py**
After agent-gsd.sh completes, `arena_run.py` reads the sandbox contents (git log, .planning/STATE.md, DONE.md, FLAG.md, result.json) and synthesizes insights.jsonl from the build artifacts. This is deterministic and does not depend on the competitor's LLM remembering to write insights.

**Approach B: Inject insights instruction into the build prompt**
Modify the instruks passed to agent-gsd.sh to include "also produce insights.jsonl with your observations." This depends on the competitor LLM (Qwen3-8b/32b) following the instruction, which is unreliable.

**Recommendation: Use Approach A.** `arena_run.py` reads result.json (produced by agent-gsd.sh), parses git log, reads DONE.md/FLAG.md, and synthesizes structured insights from concrete build artifacts. This is reliable regardless of competitor model quality.

### Anti-Patterns to Avoid
- **Running agent-gsd.sh directly from SKILL.md instructions:** The agent loop (LLM) should NOT shell out to agent-gsd.sh directly. Instead, it should call `arena_run.py` which handles all mechanics. The LLM should focus on parsing the task and invoking the script.
- **Modifying heartbeat/service.py:** The skill should work within the existing heartbeat dispatch flow. No changes to service.py are needed.
- **Storing insights in memory instead of file:** insights.jsonl must be a file in the sandbox for Phase 3 harvesting.

## Common Pitfalls

### Pitfall 1: Task Description Is Displayed Raw, Not Parsed
**What goes wrong:** `_format_tasks_for_prompt()` puts the description field verbatim into the prompt as `**Description:** {description}`. For arena tasks, the description is a JSON string. The SKILL.md must instruct the agent to parse this JSON.
**Why it happens:** The heartbeat system is generic -- it formats all tasks the same way.
**How to avoid:** SKILL.md must explicitly say: "When you receive an arena task, the Description field contains a JSON string. Parse it to extract bo_id, bo_filepath, model, and instruks."
**Warning signs:** Agent treats the JSON as plain text instructions instead of structured data.

### Pitfall 2: agent-gsd.sh Requires OAuth Session
**What goes wrong:** agent-gsd.sh explicitly `unset ANTHROPIC_API_KEY` and requires OAuth via `~/.claude/.credentials.json`. If the competitor agent's environment doesn't have a valid OAuth session, the CLI will fail.
**Why it happens:** agent-gsd.sh was designed for Claude Code with MAX subscription.
**How to avoid:** Verify that `~/.claude/.credentials.json` exists and is valid before running agent-gsd.sh. The `OCTOPUS_MODEL` overrides the model but auth still goes through Anthropic OAuth.
**Warning signs:** `claude CLI not found` or auth errors in result.json.

### Pitfall 3: Insights Must Come From Build Artifacts, Not LLM Memory
**What goes wrong:** Relying on the competitor LLM to remember to write insights.jsonl during the build. Qwen3-8b may ignore or botch the instruction.
**Why it happens:** Small models are unreliable at following multi-step instructions alongside complex build work.
**How to avoid:** `arena_run.py` should synthesize insights from concrete artifacts (result.json, git log, DONE.md, FLAG.md) after agent-gsd.sh completes.
**Warning signs:** Empty or malformed insights.jsonl, missing fields.

### Pitfall 4: Sandbox Path Must Be Absolute
**What goes wrong:** agent-gsd.sh checks for `.git` directory and initializes one if missing. If arena_run.py doesn't `cd` into the sandbox before invoking agent-gsd.sh, the git init happens in the wrong directory.
**Why it happens:** agent-gsd.sh uses relative paths internally (`. / .git / .planning`).
**How to avoid:** `arena_run.py` must set `cwd` in `subprocess.run()` to the sandbox path.
**Warning signs:** Git repo created in nanobot workspace instead of sandbox.

### Pitfall 5: Competitor Agent Config Must Exist
**What goes wrong:** The heartbeat only polls task_queue if `agent_name` is set. Competitor agents need runtime configs in `~/agents/arena-competitor-a/config.json` and must be launched with `start-agent.sh`.
**Why it happens:** No competitor agent configs exist yet.
**How to avoid:** Create configs following the dario pattern. Key fields: `agent`, `agents.defaults.workspace`, `agents.defaults.model`, `channels`, `providers`, `gateway.port`. Each competitor needs a unique port.
**Warning signs:** Tasks stay in `pending` status forever because no agent is polling for them.

### Pitfall 6: SQLite Concurrent Access From Multiple Agents
**What goes wrong:** Both competitors and the main heartbeat access `shared-memory.db` simultaneously. SQLite handles this with WAL mode but can timeout.
**Why it happens:** Multiple nanobot instances accessing the same SQLite file.
**How to avoid:** Use `timeout=5` on all sqlite3.connect() calls (already done in heartbeat/service.py). Keep transactions short.
**Warning signs:** "database is locked" errors in logs.

### message_bus INSERT Pattern
```python
import json
import sqlite3
from pathlib import Path

DB_PATH = Path.home() / "shared-data" / "db" / "shared-memory.db"

def post_result(source_agent: str, bo_id: str, model: str, status: str,
                insight_count: int, duration_s: float):
    conn = sqlite3.connect(str(DB_PATH), timeout=5)
    message = json.dumps({
        "bo_id": bo_id,
        "model": model,
        "status": status,
        "insight_count": insight_count,
        "duration_s": round(duration_s, 1),
    })
    conn.execute(
        """INSERT INTO message_bus (from_agent, to_agent, channel, message, metadata)
           VALUES (?, ?, ?, ?, ?)""",
        (source_agent, "*", "arena-build", message, json.dumps({"type": "arena-result"})),
    )
    conn.commit()
    conn.close()
```
Source: Schema from `shared-memory.db`, pattern from `arena_trigger.py`

### agent-gsd.sh Invocation Pattern
```python
import os
import subprocess
from pathlib import Path

AGENT_GSD = Path.home() / "DEV" / "garage" / "infra" / "octopus" / "agent-gsd.sh"

def run_competitor(sandbox: Path, instruks: str, model: str, bo_id: str,
                   timeout_s: int = 1800) -> dict:
    instruks_file = sandbox / "instruks.md"
    result_file = sandbox / "result.json"
    instruks_file.write_text(instruks)

    env = os.environ.copy()
    env["OCTOPUS_MODEL"] = model
    env["OCTOPUS_ORDER_ID"] = bo_id

    try:
        proc = subprocess.run(
            [str(AGENT_GSD), str(instruks_file), str(result_file), "quick"],
            cwd=str(sandbox),
            env=env,
            timeout=timeout_s,
            capture_output=True,
            text=True,
        )
        return {"exit_code": proc.returncode, "stdout": proc.stdout, "stderr": proc.stderr}
    except subprocess.TimeoutExpired:
        return {"exit_code": 1, "stdout": "", "stderr": "timeout"}
```
Source: `agent-gsd.sh` usage pattern (lines 1-23), environment variables (lines 17-21)

## Open Questions

1. **Competitor agent-home directories**
   - What we know: Runtime configs go in `~/agents/arena-competitor-{a,b}/config.json`. Identity goes in `~/DEV/operations/agent-homes/arena-competitor-{a,b}/`.
   - What's unclear: Do competitor agents need SOUL.md, USER.md, MEMORY.md, HEARTBEAT.md? Or just a minimal workspace with the arena-builder skill?
   - Recommendation: Create minimal workspaces with just SOUL.md (identity) and a `skills/` symlink to the builtin skills. The arena-builder skill will be in `nanobot/skills/` (builtin). No need for full agent-home ceremony.

2. **Insights extraction reliability**
   - What we know: agent-gsd.sh produces `result.json` with status, result text, cost, commits, git_stat fields. Also `DONE.md` or `FLAG.md`.
   - What's unclear: How rich the insights can be from build artifacts alone.
   - Recommendation: Start with basic extraction (status, duration, file count, error types) and iterate. The format allows for richer types in future versions.

3. **Claude OAuth session sharing**
   - What we know: agent-gsd.sh uses `~/.claude/.credentials.json` for OAuth. Multiple concurrent agent-gsd.sh processes would share the same OAuth session.
   - What's unclear: Whether concurrent Claude Code CLI instances with the same OAuth session cause conflicts.
   - Recommendation: Run competitors sequentially (one at a time) in v1 to avoid OAuth session contention. Parallel execution can be added later.
