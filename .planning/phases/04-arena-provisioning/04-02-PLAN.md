Fix both SQL injection vulnerabilities using a safe escaping approach compatible with psql-over-ssh (no psycopg2 available).

**Strategy: Python-side escaping helper + dollar-quoting for text fields.**

Since we pipe SQL to `psql` via stdin (subprocess), we cannot use server-side parameterized queries ($1, $2 style). Instead:

1. Create a helper function `_sql_escape(value: str) -> str` that:
   - Replaces single quotes with two single quotes (`'` -> `''`)
   - Replaces backslashes with double backslashes
   - Returns the escaped string (caller wraps in single quotes)

2. Create a helper function `_sql_escape_identifier(value: str) -> str` that:
   - Validates the value matches `^[a-zA-Z0-9_-]+$` (alphanumeric, underscore, hyphen only)
   - Raises ValueError if it contains unexpected characters
   - Returns the validated string

3. Fix `already_harvested()`:
   - Validate bo_id with `_sql_escape_identifier()` (bo_ids are like "054", "055" -- simple alphanumeric)
   - Use the validated bo_id in the SQL string

4. Fix `insert_insights()`:
   - Validate bo_id and model with `_sql_escape_identifier()`
   - Validate severity and insight_type with `_sql_escape_identifier()` (they are enum-like: "info", "warning", "error", "observation", etc.)
   - Use `_sql_escape()` for text field (free-form user content)
   - Use `_sql_escape()` for edges_json (JSON string, could contain quotes)
   - Use `_sql_escape()` for builder identity string
   - Build the SQL with escaped values

5. Add an inline comment above each function noting: `# SQL values escaped -- see _sql_escape() and _sql_escape_identifier()`

Do NOT change the psql-over-ssh transport pattern. Do NOT add psycopg2 or any external dependency. Do NOT change the function signatures. Do NOT change the summary posting code (post_summary uses sqlite3 parameterized queries with ? placeholders -- already safe).
